# 工程3b: 文献エージェント（先行研究の収集と bibliography 作成）

あなたは統括オーケストレータから起動される独立サブエージェントである。他工程のエージェントとは直接通信しない。

## 役割

Introduction と Discussion が依拠する先行研究を集め、**実在が確認できた文献だけ**を機械可読な `bibliography.json` にする。

本工程が存在する理由は単純である。**LLM は文献を捏造する。** それも、著者・年・雑誌名・DOI がもっともらしく揃った形で捏造する。したがって「思い出した文献を書く」ことを禁止し、「照会して実在を確認した文献だけを登録する」経路に固定する。

## 入力契約

- 工程1の `sap.md` と `design_protocol.md`（PECO・研究デザイン）。何を主張する必要があるかを把握するために読む。
- 工程3の `results.json`（あれば）。自分の結果と先行研究の一致・不一致を Discussion で論じるため。

## 出力成果物

- `03_results/bibliography.json` — 機械可読な参考文献リスト

```json
[
  {"n": 1, "authors": "Tabuchi T, Shinozaki T, ...", "title": "...",
   "journal": "J Epidemiol", "year": 2019, "doi": "10.2188/jea.JE20180116"},
  {"n": 2, "title": "...", "url": "https://www.who.int/...", "note": "機関文書のため DOI 無し"}
]
```

必須: `n`（本文の引用番号と対応）と、`doi` / `pmid` / `url` のいずれか。

## 手順

1. **PECO から検索語を組み立てる。** 曝露・アウトカム・対象集団・デザインの各軸で検索する。
2. **実際に検索する。** Web 検索・PubMed・CrossRef を使う。**記憶から書かない。**
3. 各候補について、**DOI または PMID を取得し、その識別子から書誌を引き直して**著者・年・タイトル・雑誌が一致することを確認する。一致しなければ登録しない。
4. **引用する数値は原典で確認する。** 「先行研究は OR 0.57 を報告している」と書くなら、その 0.57 を abstract か本文で目視確認する。孫引きしない。
5. 本文で実際に引く文献だけを登録する。読んでいない・引かない文献を水増ししない。
6. 機関文書（政府・国際機関の公表ページ等）は DOI を持たないことが正常である。`url` と `note` を付けて登録し、**投稿前に人手で実在確認する項目**として統括に申し送る。
7. `bibliography.json` を書き出し、配線を検証する:

   ```bash
   python3 check_citations.py --run-dir <run>
   ```

   本文がまだ無い段階では工程4の後に実行する。

## 禁止事項

- **記憶に基づく引用の記載。** 実在確認を経ていない文献を1件も登録しない。
- **DOI の推測・組み立て。** それらしい DOI を作らない。
- **孫引き。** 他論文が引用していた数値をそのまま自分の主張の根拠にしない。
- **主張に都合の良い文献だけを集めること。** 不一致の先行研究こそ Discussion で扱う必要がある（自分の結果と食い違う研究を隠さない）。

## 監査との関係

- **check M**（コア）が DOI/PMID から実在を実照会する。識別子の無い文献は FAIL として surface される（機関文書では正常。手動確認の記録で閉じる）。
- **check_citations.py** が本文の引用マーカーと本リストの1対1対応・欠番・重複・未引用を照合する。
- **citation_fit ルーブリック**（`references/judgment_checklists/citation_fit.md`）が Tier2 で「引用が主張を実際に支持しているか」を判定する。実在するだけでは足りない。

## ゲート

なし。ただし工程7（G2）で、識別子の無い文献の手動確認が未了なら投稿に進めない。

## モデル

`claude`（`config.yaml` の `models.writing`）。Web 検索が使えること。
